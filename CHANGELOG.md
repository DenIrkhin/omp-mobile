# Changelog

## 0.1.0 — 2026-11-15

The first release: the server for the Mac and the iPhone and iPad app, built from this repository.

### Server

- Imported the omp-sessions dashboard as `server/`.
- Added a type-check for the server, `bun run check`, and run it in CI.
- New sessions offer Claude Sonnet 5.5 · medium instead of Gemini 3.8 Flash · high, and use it when no model is sent.
- The server reads its settings from one config file, `~/.config/omp-mobile/config.json` or the file `OMP_MOBILE_CONFIG` names, instead of environment variables and constants in the code; `server/config.example.json` shows every key. Long tasks, New session, Manage, dev cycles, job reports, the page copy, the cmux sidebar sync and the local API can each be turned off there.
- The page and the server's HTTP API move under `/api/v1/`; `api/v1/README.md` describes it, and `api/v1/fixtures/` holds an example of each request and reply. The old `/api/` paths answer 404; the local API socket keeps its paths. `GET /api/v1/info` names the server and omp versions, the login and device that ask, the main profile and which modules run. Job reports on cards carry their id.
- `server/scripts/install-launchd.sh` installs the LaunchAgent `local.omp-mobile`, which starts the server at login through `server/omp-mobile-server.sh` and logs to `~/Library/Logs/omp-mobile.log`. It fills `server/launchd/local.omp-mobile.plist.template` with the checkout's path, the home folder and bun's folder, so the plist no longer holds one machine's paths.
- The server README now fits any Mac: the settings, jobs and cmux projects of the Mac it was written for moved to private notes outside the repository. It gains a modules table and a list of the names kept from omp-sessions. `server/DESIGN.md`, the original design plan, is gone; `docs/decisions.md` lists the design decisions, the root README has a quick start, and `server/THIRD_PARTY_NOTICES.md` carries omp's MIT notice. Code comments no longer name that Mac's projects, devices or jobs.
- Push, step one. The server can register devices for push notifications and send a test notification through Apple's push service with a token key. `push` in the config turns it on, off by default, with the app's bundle id, the team id and a `.p8` key per environment; `stateDir` holds `devices.json`. `POST /api/v1/devices`, `/api/v1/devices/remove` and `/api/v1/push/test` answer 404 while push is off, and `GET /api/v1/info` names the bundle id and environments when it is on. `bun scripts/push-test.ts --fake-key` checks that the Mac reaches Apple's push service without an Apple account. OmpKit decodes the device registration and its reply.
- Push, step two. While push is on, the server sends a notification when a chat starts to need input and when a job report fails, and, on devices that turn them on, for job updates and when a pinned chat finishes a long turn. It checks the chats every `push.pollSeconds` seconds only while a device is registered, never repeats a notification after a restart, sends a report written during a short downtime once, and keeps the reports it sent in `push-state.json` under `stateDir`. `push.includeSummary` decides whether a report's notification shows the first line of its summary. `api/v1/fixtures/` gains an example of each notification, and OmpKit's contract tests decode them.
- `control.ownerOnlyWords` in the config lists words of your own that make a question owner-only for `pending` and `answer` on the local API socket, on top of the built-in list: a question whose title contains one, ignoring case, is marked `ownerOnly`, and `answer` refuses it. It is empty by default.

### Phone page

- The project chips on the phone page pick one project at a time; a device that had several projects picked starts on All.
- The phone page hides New session and Reopen when New session is off, and Manage when Manage is off.

### iOS app

- `ios/OmpKit` is the Swift package the iOS app builds on. It holds the API v1 models, a client for the routes the app calls with a timeout per route, and the error texts the app shows. Its tests decode every file in `api/v1/fixtures/` and check that each request encodes like its example; the new `ios` workflow runs them when `ios/` or `api/` changes.
- OmpKit gains the phone page's list rules for the app: which chats are long tasks, search, one project chip at a time with its count, the count line and the Long tasks sections, each tested against the page's behavior. It also sets the app's theme on a chat link without touching the room key, and decides which links open in the app and which in the browser.
- OmpKit checks the server address typed at first run: it takes `my-mac.example.ts.net`, `my-mac.example.ts.net:8443` or an `https://` address and saves the server's https address; an `http://` address, a path, or something that is not a host name gets a message that says what to fix. After Connect it builds the line "Connected as <login> · server <version> · omp <version>", or asks to update the app or the server when the API version differs.
- The iOS app starts: `ios/OmpMobile.xcodeproj` builds an iPhone and iPad app for iOS 26 or later. At first run it asks for the server address, checks it with `GET /api/v1/info` and shows "Connected as …" or what went wrong, then saves it. Settings changes the address and the appearance, opens the web dashboard and shows the versions; the session list comes next. `ios/Config/Base.xcconfig` holds the build settings, and `Local.xcconfig`, copied from `Local.example.xcconfig`, a developer's own team and bundle id prefix. The `ios` workflow now builds the app too; the UI test runs on a Mac simulator.
- The iOS app shows the session list. Chats and Long tasks with their counts, search and one project chip at a time follow the phone page's rules; cards show the status, folder, session, model, job reports and a pin that moves a chat between the tabs. The list refreshes every 10 seconds while the app is in front, at once when it comes back, on pull to refresh, after a pin and when the network returns; a failed refresh keeps the last list, dimmed, under a banner with Retry. Settings opens from the gear. Watch and Control open chats in a later update.
- The iOS app opens chats. Watch opens the chat in the app and Control asks first; the chat shows the server's page copy in the app's appearance, stays loaded while you go back to the list, opens links to other sites in the browser, and shows what failed with Retry. When the server runs New session, + starts a chat in a chosen folder and model, with an optional spend cap, and opens it in Control at once; Reopen starts a closed long task's chat again. Settings can clear the cached transcripts.
- The iOS app's UI tests check the orientation rules: on an iPhone simulator the app stays in portrait when the device turns, and on an iPad simulator it turns too. The repo's checks now run the UI tests on both simulators, `omp-iPhone` and `omp-iPad`; CI still builds the app without running them.
- The iOS app gets push notifications. When the server runs push, the first run offers Allow or Not now, and Settings → Notifications has a switch, how push stands on the device, Send test and one switch per kind. The app sends its device token to the server at every launch and keeps it in memory only. A notification about the chat on screen shows no banner, and "needs input" notifications go away once the chat no longer needs input. A tap opens the chat that needs input in Control, or shows the card of a long task or a job report, highlighted with the report open, or the report in a sheet when its card is gone. Push needs a paid Apple Developer Program team; without one, Settings says so.
- The iOS app has a demo. Try the demo on the first screen shows the list with made-up chats, long tasks and job reports, answered inside the app with no Mac and no network; search, project chips and pins work, and Watch and Control open a sample chat in the app's appearance. A banner says the data is a sample, Connect your Mac leaves the demo for the server address, and Settings has Leave demo. App Review can use it to see the app.
- The iOS app is ready for App Store review. It has an app icon with light, dark and tinted variants, drawn by `ios/Design/render-icon.swift`; a privacy manifest that declares no tracking and no collected data; version 0.1.0 (1), set in `ios/Config/Base.xcconfig`; and the export-compliance answer in its Info.plist. It registers for push with its build's APNs environment: the sandbox on the Simulator and for installs from Xcode, production for TestFlight and App Store installs, which need `push.keys.production` on the server. `PRIVACY.md` is the privacy policy, and `docs/app-store.md` holds the App Store texts, the App Review notes and the screenshots.
